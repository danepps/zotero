# Bluebook Citations Fixer 2.0: Current-State Review

**Review date:** 2026-09-05

## Executive summary

The `v2.0` branch is clean, synchronized with `origin/v2.0`, and substantially
better hardened than `main`. The foundation work and style-sync implementation
are present, the Node harness passes, the JavaScript and shell files are
syntactically valid, and a temporary `1.3.3.1` build produced an XPI whose
archived manifest carried the correct version.

It is not yet a release candidate. Two planned plugin features remain unbuilt,
the two new user-facing components have not completed their required manual
verification, and the current release instructions still describe obsolete
`1.3.1.x` test builds. More importantly, invoking `build.sh` without an argument
on this branch creates an unreleased plugin under the already-released `1.3.3`
identity, while invoking it correctly for `1.3.3.1` prints instructions that
would publish that development build through the production update manifest.

The implementation itself is in good shape overall. Before a 2.0 release, I
would fix the build/release guardrails, complete manual integration testing,
make wrapper teardown and reinstallation genuinely stack-safe, add post-install
verification to style sync, and give the Word macro a guaranteed error-cleanup
path.

## Priority findings

### P0 — Development builds can collide with the released `1.3.3`

`bluebook-citations-fixer/manifest.json` is correctly left at the latest stable
version, `1.3.3`, while development versions are injected only into staged
builds. But `build.sh:18` defaults to the manifest version when no argument is
provided. On `v2.0`, therefore, running:

```sh
./bluebook-citations-fixer/build.sh
```

creates a materially different plugin labeled `1.3.3`, the same identity as
the public stable release. That can cause XPI-cache confusion, make the source
of an installed build impossible to diagnose, and prevent predictable update
ordering.

The branch history already records the correct next test version as `1.3.3.1`,
but `AGENTS.md:41`, `CLAUDE.md`, the build usage comment, and the roadmap still
refer to the obsolete `1.3.1.x` line.

**Suggested fix:** make an explicit version mandatory, or introduce explicit
`--test <version>` and `--release <version>` modes. At minimum, refuse a no-arg
build when the current branch is not the release branch, validate the version
shape, and update every live instruction to say that the next test build is
`1.3.3.1`.

### P0 — The builder tells developers to publish test builds to production

`build.sh:58-61` always prints the real-release sequence, including pushing
`update-bluebook-citations.json`. A correctly built fourth-component test XPI
therefore ends with instructions to expose that test build to every production
installation. The temporary verification build demonstrated the problem: a
`1.3.3.1` artifact was followed by directions to create a normal release and
update the production manifest.

**Suggested fix:** distinguish development and release builds. A four-component
version should print side-load or prerelease instructions and an explicit
warning not to edit the production update manifest. A release path should be
opt-in and should verify the expected three-part version, clean worktree,
release branch, update-JSON entry, tag, and asset name.

### P0 — The stable-install README advertises unreleased behavior

The README directs users to download stable `1.3.3` at line 16, but its
“Current Features” section describes automatic style sync at lines 112-119 and
the new Word macro at lines 128-154. Style sync is not on `main` or in the
released `1.3.3` XPI, and the macro is not packaged in any XPI. A user following
the install link will not receive the behavior the same page promises.

**Suggested fix:** split the page into “Released in 1.3.3” and “Unreleased on
the 2.0 branch,” or keep development documentation in the roadmap until the
feature ships. Describe the macro as a separately downloaded companion file,
not something delivered by the plugin installer.

### P0 — Required manual verification has not happened

The roadmap itself marks style sync as “pending manual verification in Zotero”
and the terminal-period macro as awaiting its in-Word self-test. These tests are
load-bearing because the Node harness mocks the Zotero integration layer and
cannot exercise preference-pane sandbox behavior, real style installation and
session reset, Word field boundaries, UndoRecord behavior, or LibreOffice.

**Suggested fix:** cut `1.3.3.1` after the build guardrails are corrected and
run a recorded verification matrix covering Zotero 7 and the supported Zotero
10 build, Word and LibreOffice RTF refreshes, startup and manual style sync,
network and validation failure, active-command deferral, disable/re-enable, and
the Word self-test. Do not call the branch a release candidate before those
results are recorded.

### P1 — Wrapper stacking is not fully safe across teardown and reinstall

The primary wrappers use identity checks during ordinary uninstall, which is a
good improvement. Three edge cases remain:

1. `patch.js:68-77` treats any prototype carrying `__lcfPatched` and
   `__bcfOrigSetText` as a stale prior instance and restores the saved original
   without first verifying that the current function is the stale BCF wrapper.
   If another plugin wrapped on top of BCF, this recovery deletes the other
   plugin's wrapper.
2. If `execCommand` or a `Session` method is overwrapped, uninstall deliberately
   leaves the chain in place but clears BCF's bookkeeping. A later install can
   adopt the entire old chain as its “original” and add another BCF layer.
3. Diagnostic concrete-field wrappers are restored unconditionally at
   `patch.js:366-380`; they do not identity-check the currently installed
   function. With diagnostics enabled, teardown can overwrite a wrapper another
   plugin installed later.

The existing lifecycle test covers only an overwrapped primary `setText` at one
uninstall, not stale recovery, reinstall, the session/exec wrappers, or
diagnostic wrappers.

**Suggested fix:** place instance-owned wrapper metadata on every patched
method, retain the exact wrapper identity for diagnostic methods, and only
restore when the live method still equals that exact wrapper. For stale
recovery, unwrap only a wrapper positively identified as BCF-owned; otherwise
leave the chain alone and report the unresolved stack. Add two-instance tests
for install → foreign wrap → uninstall → reinstall → command → uninstall.

### P1 — Style sync reports success without verifying the installed result

`style-sync.js:308-310` awaits `install()` and immediately returns `updated`.
It does not inspect the install return value or re-read the installed style.
This falls short of the earlier plan review's post-write verification
recommendation. A silent no-op, an unexpected returned ID, or an install that
resolves before the expected style metadata becomes visible will be reported as
success.

**Suggested fix:** have the install dependency return Zotero's result, then
re-read the style and verify its exact ID and parseable `updated` value against
the fetched bytes. If verification fails, report a distinct
`installed-unverified`/`failed-after-install` status; do not imply that the old
style is necessarily untouched once installation began. Add tests for wrong
return ID, missing refreshed style, stale timestamp, and successful refresh.

### P1 — The Word macro lacks guaranteed cleanup on runtime failure

`AddTerminalPeriods` disables `Application.ScreenUpdating` and starts a custom
undo record before calling `AddTerminalPeriodsIn`, but it has no error handler.
If processing a damaged/protected field, note, or document raises an error,
Word can be left with screen updating disabled and the undo record open. The
status bar also never explains the failure.

**Suggested fix:** use a single cleanup label that always ends the undo record
when started, restores the original ScreenUpdating value, and reports or
rethrows the original error. Track whether `StartCustomRecord` actually
succeeded. Add a manual protected-document/error-path test to the self-test
instructions.

### P1 — Unknown note indexes can suppress valid “Break id.” repairs

`session-run.js` records the first observed note index, including `0`, and the
author-title signature map retains the numeric minimum. `firstNoteFor()` then
takes the minimum across maps. One unknown `0` can therefore dominate a valid
positive note number, after which `id-suppress` correctly refuses to emit
`supra note 0` but unnecessarily leaves the wrong `Id.` in place.

This issue was identified in the earlier 2.0 plan review but was not included in
the implemented Phase 0 corrections.

**Suggested fix:** treat positive numbered notes and unknown indexes as
separate states. Prefer the earliest positive note whenever one exists, and use
`0` only when no positive value is known. Cover mixed `0`/positive occurrences
for both item-key and signature lookup.

### P2 — Style identity currently fails open

`patch.js:441-447` applies the Bluebook feature chain when the session's style
ID cannot be read. That avoids silently going dark, but it also means a Zotero
schema change can apply Epps-style-specific regular-expression rewrites to every
RTF citation style. The output-format gate prevents RTF corruption; it does not
prevent legally incorrect citation rewrites.

**Suggested improvement:** reconsider this policy before adding more global
pre-render hooks. Failing closed with a prominent Error Console diagnostic is
safer for style-specific transformations. If fail-open is retained, add a
runtime invariant that confirms one or more Epps-style fingerprints before
rewriting.

### P2 — Automatic style updates need a compatibility story

Style sync accepts any valid, same-ID CSL with a later `<updated>` value. That is
appropriate for ordinary style maintenance, but future changes to the Epps
style's delimiters or output shape can break the plugin's post-render anchors
without a plugin update. Multi-cite splitting already depends on literal `; `,
and several features depend on precise tail shapes.

**Suggested improvement:** add fixture/render tests against the exact currently
published built-in styles and define a compatibility mechanism for coordinated
style/plugin changes. Options include a plugin-side tested-style timestamp,
recognized style-version metadata, or a release checklist requiring the remote
CSL fixtures to pass before publication. Prefer warning and skipping a known
incompatible remote style over silently installing it.

### P2 — Built-in style metadata is duplicated in the pane

Style sync correctly obtains IDs from `BCF.patch.BUILTIN_STYLE_IDS`, but
`prefs-pane.js:35-41` maintains a second literal built-in list because the pane
runs in another sandbox. The project documentation already warns that both
locations must be edited together.

**Suggested improvement:** expose read-only built-in metadata through the
existing minimal pane bridge or load it from one packaged data file. Add a test
that compares the pane list with the patch list until the duplication is
removed.

### P2 — Scope and naming of `book-at` are broader than its name suggests

The feature does not require a book-like item type; tests intentionally cover
empty type and `report`. Its real predicate is a numeral-ending rendered title
with a page-like locator. The current filename and comments encourage a future
maintainer to add an incorrect type gate or misunderstand its Bluebook scope.

**Suggested improvement:** document the broader supported class explicitly or
rename it in a future major cleanup to something like
`numeric-title-locator-at`. Preserve the behavior and add a negative test for
an item type where `, at` would be affirmatively wrong.

### P2 — Documentation and verification hygiene have drifted

Several smaller issues should be cleaned up before release:

- `session-run.js:5-8` still says `currentSession` is cleared after a command,
  contradicting the corrected architecture and implementation.
- The roadmap still calls the removed `1.3.1.2` artifact the style-sync test
  build and its decisions log still uses the `1.3.1.x` counter.
- `AGENTS.md:37` says XPIs are force-added to the development branch even though
  the current policy and recent commits deliberately untrack built XPIs.
- `AGENTS.md` and `CLAUDE.md` have materially different architecture detail
  despite the stated mirroring rule.
- `git diff --check main...HEAD` currently fails on trailing whitespace in
  `research/2.0-plan-review.md:3`.
- The README's compatibility text says “Zotero 10 beta”; this should be checked
  against the actual supported/current Zotero release at ship time.

### P2 — Test organization is reaching its maintainability limit

The single Node harness is 2,726 lines and provides excellent regression value,
but it has no test runner metadata, coverage report, per-module isolation, or CI.
A syntax error was previously able to ship, and pane/macro behavior remains
entirely manual.

**Suggested improvement:** split tests by module while retaining one top-level
command, add a minimal package script or deterministic shell runner, and run
syntax checks, shell lint, build/archive verification, `git diff --check`, and
the Node suite in CI. Keep Zotero/Word manual gates, but make their matrix a
versioned checklist with dated results.

## Lower-priority hardening suggestions

1. Make `<updated>` parsing explicitly RFC 3339 rather than relying on the
   engine-dependent permissiveness of `Date.parse`.
2. Add a bounded loop/recheck around active-command waiting in style sync, so a
   newly active command cannot be missed after the first wait.
3. Let automatic network failures retry sooner than a full 24 hours while
   retaining backoff; currently a transient failure is treated like a completed
   successful check for throttle purposes.
4. Validate build version input before using it in a filename and `sed`
   replacement, and use `set -euo pipefail` where supported.
5. Consider removing diagnostic method monkey-patching entirely. Structured
   logging around the primary seams may provide enough evidence without
   increasing interoperability risk.
6. Record a content hash of fetched and installed CSL bytes in diagnostics. It
   would make style-sync incidents reproducible without changing the trust
   model.

## Recommended sequence

1. Decide the actual 2.0 scope: either finish et-al and journal abbreviation as
   the roadmap promises, or explicitly move them to a later release and rename
   the current milestone accordingly.
2. Fix build modes, development-version guardrails, and all stale `1.3.1.x`
   instructions.
3. Fix wrapper stack/reinstall behavior and add multi-instance lifecycle tests.
4. Add style-sync post-install verification and a compatibility gate/checklist.
5. Add guaranteed macro cleanup and run the in-Word self-test plus an error-path
   test.
6. Fix positive-note selection for `firstNoteFor()`.
7. Cut `1.3.3.1`, verify the archived manifest, and complete the manual Zotero,
   Word, and LibreOffice matrix.
8. Only after the scope is feature-complete and all gates pass, bump the working
   manifest to `2.0`, synchronize user/agent documentation, and execute the
   release/update-manifest steps in lockstep.
