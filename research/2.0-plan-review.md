# Review of the Bluebook Citations Fixer 2.0 Plan

**Review date:** 2026-07-27  
**Scope:** style sync, configurable “et al.” thresholds, render-time journal
abbreviation, and the existing `patch.js` / `session-run.js` seams on which
those features depend.

## Executive summary

The 2.0 direction is sound, but the current plans are not yet implementation
ready. The highest-priority problems are:

1. Test XPIs built with a fourth-component version do not actually contain that
   version in `manifest.json`.
2. The proposed style-sync implementation cannot guarantee its stated
   “failure never touches the local style” contract.
3. Automatic style installation can race a live word-processor integration
   command.
4. Cancelling the startup timer does not prevent an already-running style check
   from installing a style after plugin shutdown.
5. Existing async integration wrappers can fail during a hot disable or upgrade
   because they consult mutable global state after yielding.
6. The “et al.” document remains a feasibility-study plan rather than a 2.0
   implementation plan, and its proposed session-cache invalidation is unsafe.
7. The journal-abbreviation provider lacks item-type context. Identity is the
   right fallback for unknown titles, but an additional type-safety design is
   needed to protect reporters, codes, and other non-journal container titles.

The recommended sequence is to harden the build and integration seams first,
then implement style sync, convert the “et al.” study into an implementation
plan, and finally build the abbreviation engine and provider feature.

## Priority findings

### P0 — Test-build versioning does not work as documented

`bluebook-citations-fixer/build.sh` uses its version argument only to construct
the output filename:

```sh
VERSION=${1:-${MANIFEST_VERSION:?could not read version from manifest.json}}
OUT="releases/Bluebook_Citations_Fixer_v${VERSION}.xpi"
```

It then archives the working-tree `manifest.json` unchanged. Consequently:

```sh
./bluebook-citations-fixer/build.sh 1.3.1.1
```

produces a file named `Bluebook_Citations_Fixer_v1.3.1.1.xpi` whose internal
add-on version remains `1.3.1`. Zotero uses the manifest version, not the
filename, for add-on ordering and cache behavior.

This contradicts both the branch instructions and the verification step in
`research/style-sync-plan.md`.

#### Required correction

Change the build process to use a staging directory:

1. Copy the packaged files into a temporary staging directory.
2. If a version argument is provided, write that version into the staged
   `manifest.json`.
3. Zip the staged contents.
4. Leave the working-tree manifest unchanged for test builds.
5. Verify:

   ```sh
   unzip -p <xpi> manifest.json
   ```

   and require the archived version to equal the filename/version argument.

The build should fail if the staged manifest version and requested artifact
version differ. This correction should land before the first 2.0 test XPI.

### P0 — Style sync cannot currently guarantee local-style preservation

The style-sync plan promises that a network, parse, validation, or installation
failure will never uninstall or modify the local style. The proposed sequence
does not provide that guarantee.

The plan first downloads the CSL to compare `<updated>`, then calls:

```js
Zotero.Styles.install({ url: id }, id, true);
```

That creates two problems:

1. **Two-fetch race.** The bytes inspected are not necessarily the bytes
   installed.
2. **Silent-install behavior.** In Zotero’s current `Styles.install`
   implementation, validation errors are suppressed when `silent` is true, and
   installation proceeds. The installer also removes the existing style file
   before writing the replacement. A malformed-but-parseable remote style or a
   late filesystem error can therefore violate the stated invariant.

Primary source:
[Zotero `style.js`](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/style.js)
(`Zotero.Styles.install` and its internal `_install`).

#### Required correction

Use one fetched byte sequence throughout:

1. Fetch the remote CSL once.
2. Parse it as XML.
3. Require:
   - a valid `<style>` document;
   - an exact `<id>` match with the expected built-in ID;
   - a parseable `<updated>` timestamp;
   - a remote timestamp strictly newer than the local timestamp.
4. Explicitly run:

   ```js
   await Zotero.Styles.validate(remoteText);
   ```

   and treat validation rejection as a failed check.
5. Install the already-checked bytes:

   ```js
   await Zotero.Styles.install({ string: remoteText }, id, true);
   ```

6. Verify the returned `styleID`, the refreshed installed style, and its
   `updated` value.

The contract should distinguish:

- **Pre-install failures:** local style untouched.
- **Install-stage failures:** Zotero’s installer may already have modified the
  style file; restoration can only be best-effort unless the plugin implements
  its own backup/rollback machinery.

Do not promise an absolute guarantee that the underlying API cannot provide.

### P0 — Style installation must not race an integration command

`Zotero.Styles.install()` calls `Zotero.Styles.reinit()`. Current Zotero style
initialization calls `Zotero.Integration.resetSessionStyles()`, which invokes
`session.setData(session.data, true)` for every integration session.

Primary sources:

- [Zotero `style.js`](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/style.js)
- [Zotero `integration.js`](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/integration.js)
  (`resetSessionStyles` and `Session.prototype.setData`)

This corrects one plan assumption: open documents are not simply left with the
old style until reopened. Zotero actively rebuilds their style engines.

It also creates a concurrency risk. A startup check firing 60 seconds after
launch can install a style while Word or LibreOffice is in the middle of a
refresh, replacing a session’s citeproc engine during the command.

#### Required correction

Fetching and validation may occur while the application is otherwise busy, but
the installation step should wait until no integration command is active.

Use `Zotero.Integration.currentDoc` as the current active-command signal and,
when necessary, await `Zotero.Integration.currentCommandPromise` before
installation. Recheck cancellation, remote/local state, and plugin lifetime
after that wait.

No additional open-document propagation mechanism is needed after installation;
Zotero’s style reinitialization already resets session styles.

### P0 — Timer cancellation does not stop an in-flight style installation

The proposed `cancel()` method cancels only a pending `nsITimer`. Once
`check()` has begun, the async operation can continue past plugin shutdown and
initiate an installation.

Capturing `sync` and `diag` prevents dereferencing `BCF` after it becomes null,
but it does not prevent post-unload side effects.

#### Required correction

Add a lifecycle generation or cancellation token:

```js
BCF.styleSync._generation = 0;
```

- `scheduleStartupCheck()` and manual `check()` capture the current generation.
- `cancel()` increments the generation and cancels the timer.
- Every continuation after an `await` verifies that its generation remains
  current.
- The last check immediately before `install()` is mandatory.

An already-started `Styles.install()` may not be cancellable, but shutdown must
prevent any new installation from beginning.

### P0 — Existing async wrappers are unsafe during hot disable or upgrade

Several existing wrappers refer to mutable `BCF.patch` state after asynchronous
work:

```js
var origCall = function (t) {
    return BCF.patch._orig.call(field, t);
};
```

If the plugin is disabled or upgraded while `BCF.patch.run()` is pending,
`shutdown()` can null `BCF` or clear `_orig` before `origCall()` runs. That can
prevent Zotero’s original `setText()` from executing and break the document
command.

The `execCommand` and `Session.updateDocument` wrappers also use `BCF` in
`finally` blocks after awaiting the original method. An error in such a
`finally` block overrides an otherwise successful result.

#### Required correction

At wrapper invocation, capture:

- the original function;
- the patch module;
- the diagnostic module;
- any other state needed after an `await`.

Do not look those values up through global `BCF` after yielding.

Uninstallation must also restore a method only if the current method is still
the exact wrapper installed by this plugin. Unconditionally restoring the saved
original can overwrite a wrapper installed later by another plugin.

Add lifecycle tests for:

- shutdown while `patch.run()` is pending;
- shutdown while `Session.updateDocument()` is pending;
- a later third-party wrapper installed above the BCF wrapper;
- stale-wrapper recovery after an interrupted upgrade.

## Existing seam review

### `currentSession` is not a sufficient active-command signal

The repository guidance says `Zotero.Integration.currentSession` is set during
every `execCommand` and cleared in its `finally` block. Current Zotero `main`
sets `currentSession` when the command begins but, at command completion, clears
`currentDoc` and `currentWindow` rather than `currentSession`.

Primary source:
[Zotero `integration.js`](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/integration.js)
(`execCommand`).

The last session can therefore remain available after a command ends. Any new
pre-render/provider hook that treats a truthy `currentSession` as proof of an
active word-processor command can apply under stale document state.

#### Recommended correction

Add one shared helper, for example:

```js
BCF.patch._activeSession = function () {
    if (!Zotero.Integration || !Zotero.Integration.currentDoc) return null;
    return Zotero.Integration.currentSession || null;
};
```

Use it in the field rewrite path and the journal-abbreviation provider. A
plugin-maintained active-command depth/marker around `execCommand` is also
acceptable, provided it is capture-safe during shutdown.

Update `AGENTS.md` to remove the obsolete “cleared in finally” statement.

### A prewrite failure suppresses the safer per-field fallback

The `_updateDocument` wrapper catches errors from
`_prepareCitationTexts(this)`, but sets `__bcfPrewriteActive` even after a
failure. Every downstream `setText` call then short-circuits, so none of the
features receives its normal per-field fallback opportunity.

#### Recommended correction

Have `_prepareCitationTexts()` return an explicit result:

```js
{
    handled: true | false,
    reason: "rewritten" | "non-rtf" | "style-gate" | "error" | ...
}
```

Set `__bcfPrewriteActive` only when the prewrite pass completed successfully.
On a prewrite exception, leave it false so the `setText` path can try each field
independently.

For intentional non-RTF or style-gate skips, either behavior is safe because the
same gates exist in `patch.run`; consistency favors leaving the flag false.

### Unknown output format should fail closed

Both paths currently apply the RTF chain when `session.outputFormat` is empty:

```js
if (fmt && fmt !== "rtf") return;
```

This prevents the plugin from silently going dark if Zotero moves the field, but
the failure mode is unsafe: literal RTF fragments can be injected into an
unknown HTML-like format.

#### Recommended correction

Require:

```js
if (fmt !== "rtf") return;
```

Log an explicit diagnostic for an empty/unknown output format. A skipped rewrite
is safer than corrupting rendered output.

### Diagnostic concrete-field wrappers should not run unconditionally

`_instrumentSessionFields()` and `_instrumentField()` wrap raw word-processor
field prototypes even when diagnostics are disabled. Their event calls become
no-ops, but the monkey patches remain.

They also create restoration-order risks with other plugins.

#### Recommended correction

Prefer removing the raw-field instrumentation from production. If it remains
useful, install it only when `BCF.diag.enabled` is true and use identity-checked
restoration.

### Session-patch installation should have an independent readiness condition

`patch.install()` retries while `Zotero.Integration.Field` is unavailable. If
`Field` becomes available while `Session` remains unavailable,
`_installSessionPatches()` can return without installing the prewrite seam and
the retry stops after the field patch succeeds.

#### Recommended correction

Track field-patch and session-patch readiness separately. Continue bounded
retrying until all required seams are installed, or until shutdown cancels the
retry.

## `session-run.js` review

### Repeated CSL conversion is avoidable

`BCF.run._build()` calls `_fetchLibraryData(ci_)` for every citation occurrence.
A source cited many times is repeatedly fetched and converted with
`itemToCSLJSON`.

#### Recommended correction

Add a build-local cache keyed by Zotero item ID:

```js
var fetchedByID = new Map();
```

Cache both successful conversions and misses for the duration of `_build()`.
This becomes more important when the journal-abbreviation provider also needs
type/title indexes from the run context.

### The duplicate-item signature can conflate distinct editions

`_sigFor()` uses only normalized author surnames and full title. Two distinct
editions or versions of the same work can therefore share a first-note target.
The current behavior is deliberately tolerant of duplicate library items, but
its false-positive case can produce an incorrect `supra note N`.

#### Recommended correction

Consider adding stable discriminators when present:

- item type;
- issued year;
- volume or edition;
- container title for article-like items.

The precise balance should preserve duplicate-item recovery without merging
clearly different editions.

### Unknown note index can dominate a known positive index

The signature map records the numeric minimum note index. An unreadable
`noteIndex` becomes `0`, which wins over every positive note and can make
`id-suppress` reject an otherwise valid `supra` target.

This fails safely—no bad `supra` is emitted—but can unnecessarily disable the
feature.

#### Recommended correction

Prefer the earliest positive note index when any positive index exists. Use
zero only when no numbered occurrence is known.

## Style-sync plan revisions

### Keep the basic product decisions

The following choices remain sound:

- automatic, silent checks with a disable preference;
- one startup check per 24 hours;
- a manual “Check for style updates” button;
- built-in styles only;
- installed styles only;
- strictly-newer `<updated>` comparison;
- no prompt on network failure;
- a shared in-flight promise to prevent duplicate checks;
- writing `lastCheck` after failed runs so a dead network is not retried on
  every launch.

### Change the status model

The proposed `summaryLabel()` gives “updated” precedence over failure. If one
style updates and the second fails, the pane can say only “Updated to
YYYY-MM-DD,” hiding the partial failure.

Use summaries such as:

- `Up to date`
- `Updated 1 style`
- `Updated 1 style; 1 check failed`
- `1 style skipped: invalid metadata`
- `Epps Bluebook styles not installed`

Keep `failed` distinct from `skipped`; malformed timestamps and failed network
requests are operationally different.

### Avoid a second hardcoded built-in list

`styleIDs()` is described as using `BCF.patch.BUILTIN_STYLE_IDS` as its source
of truth, but the fallback contains a duplicate literal list.

Because `style-sync.js` is loaded after `patch.js`, prefer:

```js
return BCF.patch.BUILTIN_STYLE_IDS.slice();
```

If the constant is unexpectedly unavailable, log and return an empty list.
Fail closed rather than introducing another list that can drift.

### Expose a minimal pane API

The plan exposes the entire `BCF` namespace as
`Zotero.BluebookCitationsFixer`. The pane needs only a small surface:

```js
Zotero.BluebookCitationsFixer = {
    checkStyleUpdates: function () { ... },
    styleUpdateSummary: function (result) { ... }
};
```

This reduces coupling between the preference sandbox and bootstrap internals.
Delete that exact bridge object during shutdown.

### Add integration-command and shutdown tests

In addition to the proposed pure helper tests, cover:

- shutdown during fetch prevents installation;
- shutdown after validation but before installation prevents installation;
- a check waits for an active integration command to finish;
- installed bytes are the same bytes that were validated;
- wrong remote `<id>` is rejected;
- validation rejection leaves install uncalled;
- mixed result summaries disclose partial failure;
- `Styles.install` returning the wrong `styleID` is treated as failure;
- style installation triggers session resets without plugin-created session
  deletion.

## Configurable “et al.” thresholds

### The current document is not an implementation plan

`research/et-al-threshold-override-plan.md` still defines its deliverable as a
feasibility study with no plugin changes. It also retains obsolete instructions
to create a separate Claude-named branch and draft PR.

If this is a 2.0 feature, replace that document with an implementation plan
covering files, lifecycle, tests, build artifact, and manual verification on the
shared `v2.0` branch.

### Do not delete integration sessions

The plan proposes purging `_cachedEngines` and deleting entries from
`Zotero.Integration.sessions`. Deleting live sessions is unnecessary and risks
discarding document-specific integration state.

Current `getCiteProc()` uses its global engine cache only when the caller passes
the `cache` option. `Session.setData()` does not pass that option. The session
itself holds the integration engine until reset.

#### Correct propagation design

On a relevant preference change:

1. Clear optional engine caches for affected `Zotero.Style` objects using
   `clearEngineCache()`.
2. Call `await Zotero.Integration.resetSessionStyles()`.
3. Never remove entries from `Zotero.Integration.sessions`.

Serialize repeated preference changes behind one reset promise.

### Define a complete patch lifecycle

The eventual implementation needs:

- a dedicated module such as `lib/et-al-override.js`;
- `install()` and `uninstall()`;
- stale-wrapper recovery;
- identity-checked restoration;
- preference-observer registration and unregistration;
- engine-cache clearing on install, preference change, and uninstall;
- session-style reset on install, preference change, and uninstall;
- capture-safe behavior during hot disable/upgrade.

### Use a strict style-ID gate

The post-render RTF chain intentionally fails open when a session’s style ID is
unreadable. That rule should not be copied to a global
`Zotero.Style.prototype.getCiteProc` hook.

The pre-render hook runs in contexts beyond word-processor integration,
including previews and Create Bibliography. If `this.styleID` is unreadable,
the override should fail closed and delegate to Zotero unchanged.

Initially limiting this feature to the two built-in Epps styles would
substantially reduce risk. Extending arbitrary user-selected styles can be a
later feature after descendant-attribute and subsequent-citation behavior is
defined.

### Clarify output-format scope

An XML rewrite at `getCiteProc` time naturally affects RTF, HTML, and text
engines. The current verification plan nevertheless expects Google Docs to pass
through.

Choose and document one rule:

- **Recommended:** apply the preference under the allowed Epps styles in all
  output formats, since it changes citeproc input rather than injecting RTF.
- **Alternative:** explicitly gate on `format === "rtf"` in the wrapper.

The existing RTF-only limitation does not technically require the new
pre-render feature to be RTF-only.

### Simplify the user-facing preference

The motivating Bluebook choice is when truncation begins. The Epps styles
already use `et-al-use-first="1"`.

Prefer:

- `Use style default`; or
- truncate at `3`, `4`, or `5` authors;
- keep `et-al-use-first=1`.

Exposing arbitrary `useFirst` values permits outputs outside the stated
Bluebook choice and creates unnecessary validation interactions. If it is
retained, enforce at least:

```text
1 <= et-al-use-first < et-al-min
```

and account for any `et-al-use-last` constraints.

### Keep plugin-generated short forms independent

`hereinafter._authorPrefix()` and `id-suppress` generate Bluebook short-form
author prefixes: one surname, two surnames joined by `&`, and first surname
plus italicized `et al.` for three or more authors.

That is a distinct short-form rule from citeproc’s long-form citation and
bibliography name-list truncation. The new preference should not change those
plugin-generated short forms unless the UI explicitly says it does.

### Make the XML-rewriter testable

The Node harness lacks `DOMParser`. An implementation plan promising Node tests
for a DOM-based XML rewriter must specify the seam.

Options include:

- dependency-inject parser and serializer functions;
- separate DOM mutation from parsing and test the mutation with minimal mocks;
- add a bounded XML test dependency;
- test exact built-in-string fixtures with a carefully constrained transformer.

Do not silently fall back to broad regex rewriting of arbitrary CSL XML.

## Render-time journal abbreviation

### Decision: identity fallback, not MEDLINE

Under an active, allowed Bluebook integration session, an unrecognized
container title should be passed through unchanged rather than delegated to
Zotero’s MEDLINE algorithm.

Delegating unknowns produces mixed output:

- known titles use Bluebook abbreviations;
- unknown titles use MEDLINE abbreviations.

That is less predictable and harder to detect than leaving an unknown title
unabbreviated.

The provider/engine contract should be explicit rather than relying on a truthy
string:

```js
{
    recognized: true | false,
    value: "Harv. L. Rev." | null
}
```

Provider behavior:

1. Inactive command, disallowed style, non-RTF output, or non-container-title
   category: delegate to Zotero unchanged.
2. Active allowed RTF command and recognized journal title: write the Bluebook
   abbreviation.
3. Active allowed RTF command and unrecognized container title: write the
   original key unchanged.
4. Do not delegate an unrecognized allowed-session container title to MEDLINE.

### Identity alone does not solve the item-type problem

The callback:

```js
getAbbreviation(listname, obj, jurisdiction, category, key)
```

does not receive the CSL item or its type. The Epps styles currently request
short-form `container-title` for more than journal articles, including cases and
legislation. A general word engine can partially recognize a reporter or code
name and transform it even though it is not a journal.

Primary source:
[Zotero `cite.js`](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/cite.js)
(`Zotero.Cite.getAbbreviation` and `Zotero.Cite.System`).

### Preferred correction: narrow the CSL call sites

Because the Epps styles are controlled by the same project, the cleanest design
is to remove `form="short"` from non-journal `container-title` branches,
particularly:

- `legal_case`;
- `legislation`;
- non-journal authorless short-form branches.

Those branches already store the desired reporter/code/container value and do
not need a journal-abbreviation provider. Keep `form="short"` on the
`article-journal` branches that should invoke the Bluebook abbreviation system.

This eliminates most item-type ambiguity at the source. Publish the corrected
CSL with a newer `<updated>` timestamp so style sync distributes it.

### Fallback correction if the CSL cannot be changed

Build two normalized title sets from the active session:

- journal container titles eligible for abbreviation;
- non-journal container titles that must remain unchanged.

Decision order:

1. If a key appears in the non-journal deny set, return identity.
2. Else if it appears in the journal allow set, run the Bluebook engine.
3. Else return identity.

Deny wins on collision. This safely under-abbreviates rather than risking a bad
reporter or code abbreviation.

The limitation is bibliography-only uncited items that are absent from
`citationsByIndex`; they may remain unabbreviated unless the session index is
expanded to include bibliography data.

### Require an actually active integration command

The current feasibility document checks:

```js
var s = Zotero.Integration.currentSession;
```

That is insufficient because `currentSession` can remain stale. Require
`currentDoc` or the shared active-command helper described above.

### Apply the promised output-format gate

The feasibility document says the feature is RTF-only, but its provider sample
does not check `session.outputFormat`.

If RTF-only remains the chosen scope, require `fmt === "rtf"` before replacing
MEDLINE. Under Google Docs/HTML, delegate to Zotero.

Unlike the “et al.” XML override, this is a product choice rather than a
technical requirement; the provider itself is not RTF-specific.

### Reset engines on provider install and uninstall

`Zotero.Cite.System` copies `Zotero.Cite.getAbbreviation` into each new system
object when automatic journal abbreviations are enabled. Existing engines can
therefore retain:

- Zotero’s original provider after the plugin installs its wrapper; or
- the plugin wrapper after the plugin is disabled.

After installing or uninstalling the provider wrapper:

1. clear relevant style engine caches; and
2. call `Zotero.Integration.resetSessionStyles()`.

Use the same active-command serialization and lifecycle protections as the
“et al.” override.

### Add provider-specific verification

Unit/integration coverage should include:

- known journal title → Bluebook abbreviation;
- unknown journal title → exact identity, never MEDLINE;
- reporter (`U.S.`, `F.3d`, etc.) → identity;
- legislation/code container → identity;
- partial common-word match in a non-journal title → identity;
- journal/non-journal title collision → deny wins;
- stale `currentSession` with no active `currentDoc` → delegate;
- HTML/Google Docs → delegate if the feature remains RTF-only;
- provider install followed by session reset;
- provider uninstall followed by session reset;
- hot shutdown while an integration command is rendering;
- cited bibliography entries match their citation abbreviations;
- uncited bibliography-only behavior is documented and tested.

### Phase 0 — Correct the foundation

1. Fix staged test-build version injection.
2. Add XPI manifest/content validation.
3. Harden all existing async wrappers against shutdown.
4. Make uninstall restoration identity-safe.
5. Remove or diag-gate raw-field instrumentation.
6. Add an active-session helper using `currentDoc`.
7. Make unknown output formats fail closed.
8. Restore the per-field fallback after a failed prewrite pass.
9. Add per-item CSL conversion caching in `session-run.js`.
10. Add lifecycle and wrapper-stacking tests.

Produce the first 2.0 test XPI only after its archived manifest is verified to
contain `1.3.1.1`.

### Phase 1 — Implement style sync

1. Implement pure timestamp/result helpers.
2. Fetch remote CSL once.
3. Parse and verify exact style ID.
4. Explicitly validate CSL.
5. Wait for any active integration command.
6. Recheck lifecycle generation and state.
7. Install the validated string.
8. Verify the refreshed installed style.
9. Add honest mixed-result status messages.
10. Add the manual Settings-pane action through a minimal bridge.
11. Exercise startup throttle, manual bypass, failure, shutdown, and
    integration-command races.

### Phase 2 — Implement the “et al.” override

1. Replace the feasibility-study plan with an implementation plan.
2. Initially scope the override to the built-in Epps styles.
3. Implement a DOM-based pre-parse XML rewrite.
4. Expose one threshold preference with `use-first=1`, unless broader controls
   are expressly required.
5. Implement patch lifecycle and preference observers.
6. Clear optional style caches and call `resetSessionStyles()` on changes.
7. Test RTF, HTML, text/preview, citations, and bibliography according to the

### Phase 3 — Build the abbreviation engine

1. Build the pure `engine.abbreviate()` spike first.
2. Require fixture coverage for every notation/data convention.
3. Return structured recognition metadata, not just a string.
4. Validate the institutional-aware spacing pass separately.
5. Resolve source/licensing decisions before transcribing a large table.

### Phase 4 — Implement the journal provider

## Release gate

Version 2.0 should not ship until all of the following are true:

- The XPI’s internal manifest version is `2.0`.
- The test-build mechanism has demonstrated correctly ordered fourth-component
  versions.
- Node tests pass.
- New lifecycle and provider tests pass.
- Manual Word and LibreOffice verification passes.
- All network/style-install failures are accurately reported and have the
  documented local-style effect.
- Provider fallbacks never emit MEDLINE under an active allowed Bluebook session.
- Cases and legislation are protected from journal-title transformation.
- Preference changes rebuild engines without deleting integration sessions.
- Hot disable/upgrade does not prevent Zotero’s original methods from completing.
- `update-bluebook-citations.json`, the release tag, asset URL, and manifest
  version agree.
- The release URL resolves before the updated auto-update manifest reaches
  `main`.
- The temporary `v2.0` branch paragraph is removed from `AGENTS.md`.
- User-facing README and release history describe all three features and their
  output-format limitations accurately.

## Bottom line

Style sync remains the right next feature, but it should be preceded by a small
foundation change that fixes test-build versioning and hardens the integration
wrappers. The style-sync implementation should then use a one-fetch,
explicitly-validated installation path, serialize installation against active
document commands, and prevent post-shutdown side effects.

The “et al.” override is feasible but needs a real implementation plan and
should reset engines rather than delete sessions. The journal-abbreviation
provider should use identity—not MEDLINE—for unknown titles, but it also needs a
type-safety solution. Narrowing the Epps CSL’s `form="short"` call sites is the
cleanest solution; session allow/deny sets are the safe fallback.
